### B4-1 · Skill 개요 · 구조 (14:00~14:10 · 10분)

#### 1단계 — 왜 Skill 인가 (3분)

> "오후 시작하겠습니다. 오전에 제가 마지막에 질문 하나 던졌죠.
>
> **모든 규칙을 CLAUDE.md 에 넣으면 될까요?**
>
> 안 됩니다. 이유가 두 개입니다.
>
> 첫째, **길면 희석됩니다.** 오전에 말씀드렸죠.
>
> 둘째, 이게 더 중요한데요. **대부분의 작업에서 안 쓰이는 지식** 이 있습니다.
>
> 예를 들어볼게요. 우리 관제 콘솔에 **DTC 코드** 라는 게 나옵니다. 차량 진단 코드요. `P0420`, `C1234` 이런 거.
>
> 이걸 해석하는 방법을 CLAUDE.md 에 쓴다고 쳐봅시다. 코드 체계 설명하고, 심각도 기준 적고, 대응 절차 적고. 200줄쯤 되겠네요.
>
> 그런데 여러분이 하는 작업 열 개 중에 DTC 해석이 필요한 건 몇 개일까요? **한 개나 될까 말까입니다.**
>
> 나머지 아홉 번은 그 200줄이 **자리만 차지하고 다른 규칙을 희석시킵니다.**
>
> 그래서 나온 게 Skill 입니다."

**판서**

```
CLAUDE.md    항상 로드     →  자주 쓰는 규칙, 짧게
Skills       필요할 때만   →  가끔 쓰는 전문 지식, 길어도 됨

           "AI가 스스로 판단해서 꺼내 읽는 참고서"
```

#### 2단계 — Skill 의 구조 (4분)

> "구조는 아주 단순합니다. **폴더 하나에 `SKILL.md` 파일 하나.** 끝입니다."

**판서**

```
.claude/skills/
└─ dtc-explainer/
   ├─ SKILL.md           ← 필수
   └─ reference/         ← 선택. 길어지면 여기로 분리
      └─ dtc_codes.md
```

**화면 — `SKILL.md` 골격 표시**

```markdown
---
name: dtc-explainer
description: 차량 진단코드(DTC)를 신입 눈높이로 해설한다.
             "DTC", "진단코드", "P0420", "고장코드" 같은 요청 시 사용한다.
---

# DTC Explainer

## 실행 절차
1. ...

## 출력 형식
...

## 규칙
- ...
```

> "위에 `---` 사이에 들어가는 걸 **frontmatter** 라고 합니다. 여기 두 개가 들어갑니다.
>
> `name` 은 스킬 이름. 폴더 이름이랑 같게 씁니다.
>
> `description` 이 **오늘의 핵심** 입니다. 잠시 후에 자세히 하겠습니다.
>
> 아래 본문에는 세 가지를 씁니다."

**판서**

```
① 실행 절차   호출되면 무슨 순서로 일할지
② 출력 형식   결과물의 목차를 고정      ← 예시 1개가 설명 10줄보다 강하다
③ 규칙        하지 말아야 할 것
```

#### 3단계 — description 이 전부다 (3분)

> "이제 제일 중요한 얘기입니다.
>
> 여러분이 스킬을 아무리 잘 써도, **AI가 그 스킬을 안 부르면 없는 겁니다.**
>
> 그럼 AI는 어떻게 부를지 말지를 정할까요? **`description` 만 봅니다.**
>
> 본문은 안 봅니다. 부르기로 결정한 다음에야 봅니다.
>
> 그래서 `description` 은 **설명문이 아니라 트리거** 입니다."

**판서 — description 공식**

```
<무엇을 한다>.  <트리거 단어들>이 나올 때 사용한다.

❌ "코드를 설명합니다"
   → 너무 넓다. 언제 부를지 알 수 없다.

✅ "차량 진단코드(DTC)를 신입 눈높이로 해설한다.
    'DTC', '진단코드', 'P0420', '고장코드' 요청 시 사용한다."
   → 트리거 단어가 박혀 있다.
```

> "말로 하면 잘 안 와닿습니다. **실패하는 걸 직접 보여드리겠습니다.**"

### B4-2 · LAB_4-1 손코딩 + LAB_4-2 description 함정 (14:10~14:20 · 10분)

#### LAB_4-1 · `dtc-explainer` 손코딩 (5분)

>
> **일부러 description 을 부실하게 쓰겠습니다.** 이유는 곧 아실 겁니다."

**시연용 SKILL.md — ① 나쁜 버전 (LAB_4-2 전용)**

```markdown
---
name: dtc-explainer
description: 코드를 설명합니다.
---

# DTC Explainer

## 실행 절차
1. 입력된 진단코드를 확인한다
2. 코드 체계에 따라 계통을 판별한다
3. 신입 정비사도 이해할 수 있는 비유로 설명한다

## 출력 형식

| 항목 | 내용 |
| --- | --- |
| 코드 | P0420 |
| 계통 | 파워트레인 |
| 정의 주체 | SAE 표준 / 제조사 |
| 심각도 | CRITICAL / WARNING / INFO |
| 증상 | |
| 예상 원인 | |
| 비유 | 한 문장 |

## 규칙
- 정의되지 않은 코드는 **추측하지 않는다.** "제조사 확인 필요" 로 응답한다.
- 심각도를 임의로 판단하지 않는다.
```

> "자, 만들었습니다. 절차도 있고, 출력 형식도 있고, 규칙도 있습니다. **본문은 꽤 잘 썼죠.**
>
> 이제 불러보겠습니다. 새 세션에서요. **스킬 이름은 부르지 않겠습니다.** 실무에서 여러분이 말하는 것처럼 하겠습니다."

**입력 프롬프트**

```
P0420 이 무슨 코드야? 신입도 알아듣게 설명해줘.
```

> "(결과 확인)
>
> 답은 했습니다. 그런데 보세요. **제가 만든 출력 형식이 아닙니다.** 그냥 자기 말로 설명하고 있죠.
>
> **스킬이 호출되지 않은 겁니다.**
>
> 본문을 그렇게 잘 썼는데요. 왜일까요?"

#### LAB_4-2 · description 교체 (5분)

> "`description` 을 보시죠. **'코드를 설명합니다.'**
>
> AI 입장에서 생각해봅시다. 세상에 '코드'가 몇 종류입니까? 소스코드, 우편번호, 상품코드, 에러코드.
>
> **너무 넓어서 언제 써야 할지 알 수가 없습니다.** 그래서 안 부른 겁니다.
>
> 딱 한 줄만 바꾸겠습니다."

**교체 — ② 좋은 버전**

```markdown
description: 차량 진단코드(DTC)를 신입 눈높이로 해설한다.
             "DTC", "진단코드", "고장코드", "P0420" 같은 코드값이
             언급될 때 사용한다.
```

> "본문은 **한 글자도 안 건드렸습니다.** description 한 줄만 바꿨습니다.
>
> 다시 물어보겠습니다. 똑같은 질문으로."

**입력 (동일 프롬프트)**

```
P0420 이 무슨 코드야? 신입도 알아듣게 설명해줘.
```

> "(결과 확인)
>
> **불렸습니다.** 제가 정한 표 형식으로 나오죠. 계통, 심각도, 비유까지.
>
> 정리하겠습니다."

**판서**

```
스킬이 안 불린다  =  본문이 나빠서가 아니라  description 이 나빠서다

본문   →  불린 다음에 읽힘
description  →  부를지 말지를 결정함     ← 여기가 전부
```

> "하나만 더 보여드리겠습니다. 아까 규칙에 **'정의되지 않은 코드는 추측하지 않는다'** 라고 썼죠. 이거 테스트해보겠습니다."

**입력**

```
C1234 는 무슨 코드야?
```

> "(결과 확인) **'제조사 정의 코드로, 표준 정의가 없습니다. 제조사 확인이 필요합니다.'**
>
> 좋습니다. 지어내지 않았어요.
>
> 이게 왜 중요하냐면요. `C1234` 는 실제로 **제조사가 각자 정의하는 코드** 입니다. 표준에 없어요.
>
> AI한테 그냥 물어보면? **그럴듯하게 지어냅니다.** 'ABS 휠속도 센서 이상' 같은 걸로요. 맞을 수도 있고 아닐 수도 있습니다.
>
> **정비 현장에서 이건 사고입니다.** 그래서 규칙에 '추측 금지' 를 박아둔 겁니다.
>
> 스킬은 **AI가 아는 척하는 걸 막는 도구이기도 합니다.**"

> **자산 메모** — `dtc-explainer` 스킬은 저장소에 없다. 위 두 버전을 **강사가 당일 손코딩**하는 것이 LAB 설계다. 사전에 두 버전을 파일로 준비해두고, 화면에서는 타이핑하는 것처럼 붙여넣으면 시간이 절약된다.
>
> 참고 데이터 — `module_7/tracks/H1_dtc_dictionary/data/dtc_codes.json` 에 `P0420`(SAE 정의, WARNING) 과 `C1234`(제조사 정의, 값 전부 `null`) 가 실제로 들어 있다. 다만 이 파일은 **7교시 H1 트랙 데이터**이므로, 통째로 열지 말고 두 코드만 발췌해 쓸 것.

> 읽어보시면 아시겠지만, **엄청 부실합니다.** '크게 복잡할 필요 없고 다음 달까지 되면 좋겠습니다' 이런 수준이에요. 실무에서 오는 요청이 딱 이렇죠.
>
> 여러분이 할 일은 네 단계입니다."

**판서 — 시간 배분**

```
0~3분    prd-creator 스킬 완성      ⬜ 채우기
3~5분    내 스킬로 PRD v1 생성       ← 스킬 이름 부르지 말 것
5~7분    grill-me 로 심문
7~10분   지적 반영해서 v2
```

> "세 가지만 강조하겠습니다.
>
> 첫째, **3분 안에 스킬을 끝내세요.** 스킬 다듬느라 PRD 못 만드는 게 제일 흔한 실패입니다. `skill-creator` 쓰셔도 됩니다.
>
> 둘째, PRD 만들 때 **스킬 이름을 부르지 마세요.** '`prd-creator` 로 만들어줘' 하면 반칙입니다. 그냥 'PRD 작성해줘' 라고 하세요. **description 이 트리거로 작동하는지가 채점 대상** 입니다.
>
> 셋째, 이게 중요한데요. grill-me 가 지적하는 걸 **전부 받아들이지 마세요.**
>
> **최소 1건은 거부하고, 왜 거부하는지 사유를 적으세요.**
>
> 왜냐면요. AI가 지적한다고 다 맞는 게 아닙니다. '임원 우선권을 정의해야 한다' 고 지적할 수 있는데, 여러분이 '**우리 회사 규모에서는 과잉 설계다. v1 범위 밖으로 둔다**' 고 판단할 수 있어요.
>
> **그 판단이 여러분의 일입니다.** 맹종하면 AI 밑에서 일하는 거예요.
>
> 시작하세요."
