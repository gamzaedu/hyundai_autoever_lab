> "(실행 중) 보세요. 파일을 하나씩 읽고 있습니다. `App.tsx` 읽고, `VehicleTable.tsx` 읽고, `alarms.ts` 읽고.
>
> **이 파일 내용이 전부 제 대화창에 쌓이고 있습니다.**

### B5-2 · 멀티에이전트 오케스트레이션 (15:10~15:20 · 10분)

#### 1단계 — 구조 (3분)

**판서**

```
        [ 나 · 메인 세션 ]
              │
      ┌───────┼───────┐
      ▼       ▼       ▼
   에이전트1 에이전트2 에이전트3     ← 각자 독립된 컨텍스트
      │       │       │
      └───────┼───────┘
              ▼
         [ 요약만 회수 ]
```

> "구조는 단순합니다. 메인 세션이 **오케스트레이터** 입니다. 지휘자예요.
>
> 지휘자가 하는 일은 두 개입니다. **일을 쪼개서 나눠주고, 결과를 합칩니다.**
>
> 중요한 건 이겁니다. **에이전트끼리는 서로 모릅니다.** 1번이 뭘 봤는지 2번은 모릅니다.
>
> 이게 장점이자 단점입니다. 장점부터 보시죠."

#### 2단계 — 시야 제한이 왜 품질을 올리는가 (4분)

> "여러분 코드 리뷰 받아보신 적 있죠. 이런 리뷰 받아보셨을 겁니다.
>
> '음... 전반적으로 괜찮은데, 여기 변수명이 좀 그렇고, 아 그리고 이건 성능이 좀 걱정되고, 보안도 봐야 할 것 같고...'
>
> **뭘 고쳐야 할지 모르겠는 리뷰죠.**
>
> AI한테 '이 코드 리뷰해줘' 하면 정확히 이게 나옵니다. **넓고 얕게** 봅니다.
>
> 그런데 이렇게 물으면 다릅니다. **'너는 보안 담당이다. 보안만 봐라. 성능이나 네이밍은 보고하지 마라.'**
>
> 갑자기 깊어집니다. 왜 그럴까요?"

> (답을 받는다)

> "**볼 게 줄었으니까요.** 같은 주의력을 좁은 데 씁니다.
>
> 사람도 똑같습니다. 보안 전문가한테 리뷰 맡기면 보안만 깊게 봅니다. 그래서 팀에 역할을 나누는 거죠.
>
> 이걸 AI한테도 그대로 합니다."

**판서**

```
"이 코드 리뷰해줘"           →  넓고 얕게. 다 조금씩.
"너는 보안 담당. 보안만"      →  좁고 깊게.

시야 제한  =  주의력 집중  =  탐지율 상승
```

#### 3단계 — 언제 쓰고 언제 안 쓰는가 (3분)

**판서**

```
✅ 서브에이전트가 잘하는 것        ❌ 못하는 것
─────────────────────────────────────────────────
탐색 · 조사 · 파악                같은 파일을 동시에 수정
독립적인 검토 (보안/성능/컨벤션)    앞 결과에 의존하는 순차 작업
대량 파일 읽기                    서로 합의가 필요한 작업

     한마디로  →  읽기에 강하고,  쓰기에 약하다
```

> "이 한 줄만 기억하세요. **읽기에 강하고 쓰기에 약합니다.**
>
> 왜 쓰기에 약한지는 잠시 후에 **직접 보여드리겠습니다.** 사고 장면으로요."

### B5-3 · 역할 부여 (15:20~15:30 · 10분)

#### 1단계 — 정의 파일 구조 (3분)

> "역할을 어떻게 주냐. 파일로 줍니다. **스킬이랑 구조가 거의 같습니다.**"

**판서**

```
.claude/agents/
├─ security-reviewer.md
├─ performance-reviewer.md
└─ convention-reviewer.md
```

**화면 — `module_5/agents/security-reviewer.md` 를 열어 함께 읽는다**

```markdown
---
name: security-reviewer
description: 코드의 보안 취약점만 점검한다. "보안 리뷰", "취약점 점검",
             "시크릿 노출 확인" 요청 시 사용한다.
tools: Read, Grep, Glob
---

당신은 커넥티드카 백엔드/프론트엔드를 담당하는 **보안 리뷰어**다.

## 점검 범위 (이것만 본다)
...

## 점검 범위 밖 (보고하지 않는다)
- 성능 · 알고리즘 복잡도
- 네이밍 · 코드 스타일 · 데드코드
- UI/UX

## 출력 형식
| # | 심각도 | 분류 | 파일:라인 | 문제 | 공격 시나리오 | 수정안 |
```

> "네 군데를 보세요.
>
> 첫째, **`tools: Read, Grep, Glob`.** 이 에이전트는 **읽기만 할 수 있습니다.** 쓰기 도구가 없어요. 리뷰어한테 수정 권한을 주면 안 되니까요.
>
> 이게 꽤 중요합니다. **역할에 맞는 도구만 주는 것** 도 하네스입니다.
>
> 둘째, **'점검 범위 (이것만 본다)'.** 볼 걸 명시했습니다.
>
> 셋째, 이게 더 중요한데요. **'점검 범위 밖 (보고하지 않는다)'.**
>
> 뭘 보라고 하는 것보다 **뭘 보지 말라고 하는 게** 효과가 큽니다. 안 그러면 보안 리뷰어가 변수명 지적하고 앉아 있어요.
>
> 넷째, **출력 형식이 표로 고정** 돼 있습니다. 3명이 각자 다른 형식으로 보고하면 합칠 수가 없습니다.
>
> 그리고 맨 아래 규칙 하나 보세요. **'근거 없는 추정은 보고하지 않는다. 파일:라인을 특정할 수 없으면 제외한다.'**
>
> 이게 왜 있는지는 실습에서 아시게 됩니다."

> **아무도 남의 영역을 침범하지 않았습니다.** 그래서 겹치지 않고, 중복 없이 합쳐집니다.
>
> 여기서 하나 짚고 넘어가겠습니다. 5번 결함 보세요. **`except: pass`**.
>
> 이게 왜 무서운 결함이냐면요. **에러가 안 납니다.** 로그도 안 남습니다. 그냥 조용히 알람이 사라집니다.
>
> 관제 시스템에서 알람이 조용히 사라지는 건 **사고입니다.** 그리고 아무도 모릅니다.

>
